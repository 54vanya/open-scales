# Design

## Context

- `Recipe` (`recipe/Recipe.kt`) хранит цели коэффициентами к дозе, тексты — `Text.Res` (встроенные) или `Text.Plain`. Проверка неубывания целей стоит в `init` и бросает исключение.
- Все рецепты берутся из `BuiltInRecipes`: список на вкладке (`MainActivity` → `RecipesScreen`) и поиск по id в `BrewActivity` (`BuiltInRecipes.byId`).
- Хранилище — только DataStore Preferences (весы, настройки). Сериализации JSON в зависимостях нет.
- Юнит-тесты идут на JVM без Android. `org.json` там — заглушка из `android.jar`.
- UI: отдельная Activity на экран, `SegmentedListItem` в списке, `StepCard` и `HintRow` — приватные функции в `BrewScreens.kt`.

## Goals / Non-Goals

**Goals:**
- Редактор своих рецептов и хранилище, которое может стать форматом обмена без миграции.
- Логика черновика (порядок, вставка, проверка, пересчёт времени, преобразование в `Recipe`) — чистый Kotlin с юнит-тестами.

**Non-Goals:**
- Экспорт, импорт и «поделиться».
- Перетаскивание элементов.
- Сохранение правок редактора при смерти процесса. Поворот переживается через ViewModel, как у варки.
- Правка встроенных рецептов и их скрытие.

## Decisions

### Рецепт хранит целые граммы, а не коэффициенты

`Recipe` переходит с `targetRatio: Double?` на `targetG: Int?`, а `defaultDoseG` — с `Double` на `Int`. `targetG` — это рубеж в граммах при дозе по умолчанию. Коэффициент отдельно не хранится. Цели при варке считаются `targetsG(doseG) = targetG × doseG / defaultDoseG`, и дробь появляется только в показе, где она и так округляется. Поведение варки не меняется: при дозе по умолчанию цели ровно те же, при другой дозе масштабируются так же.

Встроенные рецепты уже записаны граммами через `step(…, targetG)` и делят на дозу только внутри `BuiltInRecipes`. Это деление убирается. Хоффман переписывается на 30/150/250 вместо `2.0`, `10.0`, `50/3`.

Почему так: при коэффициентах любая копия встроенного рецепта или повторное открытие в редакторе требует обратного пересчёта с дробями (`50/3 × 15 = 250.00000000000003`) и округления. С целыми граммами в модели, редакторе и файле такой проблемы нет. Альтернатива — коэффициенты в модели плюс граммы в черновике с округлением при копировании. Отвергнута: плавающая арифметика в хранимых данных.

### Черновик отдельно от `Recipe`

`RecipeDraft` (`recipe/`) хранит то, что вводит человек. Поля:
- `id`;
- `title`;
- `doseG`;
- `category`;
- `description`;
- список `DraftItem`. У шага: название, длительность и комментарий строками плюс рубеж. У подписи: текст.

Поля хранятся строками, как введены: промежуточное состояние («», «1:») допустимо, а разбор в числа идёт в проверке. Каждый элемент черновика получает локальный `key` (счётчик). Его используют ключи `LazyColumn` и множество раскрытых карточек: так раскрытость не путается при перестановке.

`draft.toRecipe()` (только для прошедшего проверку черновика) строит `Recipe` с `Text.Plain` и теми же целыми граммами. `Recipe.toDraft(resolve)` переносит числа как есть, а тексты берёт на текущем языке (resolver из `Context.getString`).

Почему не редактировать `Recipe` напрямую: неубывание рубежей и длительность больше нуля проверяются в `init` исключением, а редактору нужно промежуточное неверное состояние.

### Проверка — чистая функция

`validate(draft): List<DraftError>`, где ошибка — пара «ключ элемента (или шапка) + поле + вид». Экран показывает ошибки по полям. Ошибки пересчитываются на каждое изменение, но показываются только после первого «Сохранить» (флаг `showErrors`). Так поле перестаёт быть подсвеченным, как только его исправили. Длительность хранится цифрами по маске «м:сс»: `parseDuration("130") = 90`, `parseDuration("045") = 45`; меньше трёх цифр или секунд больше 59 — `null`. Цифровая клавиатура Android не даёт набрать двоеточие, поэтому поле принимает только цифры (не больше трёх, до 9:59), а двоеточие рисует `VisualTransformation`: сразу после первой цифры, затем перед двумя цифрами секунд («1» → «1:», «13» → «1:3», «130» → «1:30»). Вариант «как таймер» (цифры заполняются справа, «5» → «0:05») отвергнут на телефоне: цифры сдвигались при наборе.

### Хранилище: файл JSON на рецепт, kotlinx.serialization

`RecipeStore` (`data/`) хранит файлы `filesDir/recipes/<uuid>.json` и отдаёт `StateFlow<List<Recipe>>`, загруженный при старте на `Dispatchers.IO`. Файл, чьё имя не совпадает с id внутри, пропускается: иначе «Удалить» стёрло бы не тот файл. Запись идёт во временный файл с переименованием, чтобы сбой не оставил полфайла. Удаление — удаление файла. Мутирует список только главный поток: `appScope`, как у репозитория весов.

Формат (DTO отдельно от модели, версия `format: 1`):

```json
{ "format": 1, "id": "…uuid…", "title": "…", "category": "pour_over", "doseG": 15,
  "description": "…", "items": [
    { "type": "step", "title": "…", "durationS": 12, "targetG": 30, "note": "…" },
    { "type": "hint", "text": "…" } ] }
```

Файл, который не разобрался или имеет `format` новее известного, пропускается и пишется в лог. Остальные рецепты при этом загружаются.

Файл на рецепт, потому что «поделиться» в будущем — это отправить один документ, а испорченный файл не тянет за собой остальные. Альтернатива — одна строка JSON в DataStore: проще, но всё переписывается целиком, и нет естественной единицы обмена.

Почему kotlinx.serialization, а не `org.json`: `org.json` не работает в JVM-тестах, а ручной разбор — лишний код. Цена — зависимость `kotlinx-serialization-json` и плагин `org.jetbrains.kotlin.plugin.serialization` той же версии Kotlin.

### Доступ к рецептам по id

`OpenScalesApp.recipeById(id)` ищет среди встроенных, затем через `RecipeStore.get(id)`. Id своих — `user:<uuid>`, встроенных — `builtin:…`, так что пространства не пересекаются. `BrewActivity` ищет через каталог. Рецепт должен быть известен синхронно в `onCreate`, поэтому берётся текущее значение `StateFlow`: к моменту касания в списке оно уже загружено. Если список ещё не загружен (процесс восстановлен прямо в экран варки), `get` читает один маленький файл с диска сразу. Если рецепта нет (удалён), экран закрывается, как сейчас при неизвестном id.

### Экран редактора

`RecipeEditorActivity` + `RecipeEditorViewModel` (черновик, исходный черновик для «есть правки», раскрытые ключи, `showErrors`). Режим и исходные данные передаются в `Intent`: `new`, `edit <id>`, `copy <id>`. Состав экрана:
- `Scaffold` с `TopAppBar`;
- `LazyColumn`: шапка, затем для каждого элемента пара «+» и элемент, в конце «+»;
- закреплённый снизу `Row` с `OutlinedButton` «Отменить» и `Button` «Сохранить».

Свёрнутые карточки должны выглядеть как на варке. Для этого `StepCard` и `HintRow` выносятся из `BrewScreens.kt` в общий файл (`ui/recipes/RecipeItems.kt`) с параметрами для режима редактора: без воды и остатка, с рубежом справа. Раскрытая карточка — `Card` с `containerColor = secondaryContainer`. Свёрнутый и раскрытый вид сменяет `AnimatedContent` с перекрёстным растворением: старый вид гаснет одновременно с проявлением нового (250 мс), `SizeTransform` за то же время меняет высоту. Стандартный переход Compose (сначала гаснет, потом с задержкой проявляется) давал заметную «пустоту» посередине. При сворачивании и удалении карточки фокус снимается, иначе на экране остаётся ручка курсора. `animateContentSize` не подошёл: при сворачивании маленькая карточка появлялась сразу, а плавно уменьшалось только пустое место под ней, и сворачивание выглядело мгновенным. Также используется `Modifier.animateItem()` в `LazyColumn`, чтобы перестановки и вставки не прыгали. Заголовок раскрытой карточки: вид элемента, иконки «вверх», «вниз», «удалить» и касание для сворачивания. «+» — небольшая `FilledTonalIconButton` по центру. Выбор вида — `DropdownMenu` с «Шаг» и «Подпись».

Поля — `OutlinedTextField` с `isError` и `supportingText`. Для дозы и рубежа — `KeyboardType.Number`, только цифры. Способ — `ConnectedChoice`, как в настройках темы.

Прокрутка к первой ошибке — `LazyListState.animateScrollToItem` по индексу карточки.

### Вкладка «Рецепты»

`RecipesScreen` получает `userRecipes` и колбэки `onEdit`, `onCopy`, `onDelete`. Долгое нажатие — параметр `onLongClick` у `SegmentedListItem` (есть в alpha28). Меню — `DropdownMenu`, привязанный к невидимой точке в месте касания (позиция первого касания ловится `pointerInput` без поглощения событий), чтобы меню открывалось у пальца; подтверждение удаления — `AlertDialog` там же, сама операция идёт в `app.appScope`. FAB «Новый рецепт» — `ExtendedFloatingActionButton` в `Scaffold` главного экрана (слот `recipesFab` у `DashboardScreen`), виден только на вкладке «Рецепты»; список получает нижний отступ, чтобы кнопка не закрывала последний рецепт.

### Правка с экрана варки

Кнопка «Изменить» в заголовке «Зерна» у своих рецептов открывает тот же редактор. `BrewViewModel` держит рецепт в `StateFlow`, `BrewActivity` слушает хранилище и передаёт новую версию в `updateRecipe`. Замена принимается только на «Зерне»: после «Далее» доза и цели зафиксированы, менять шаги посреди варки нельзя. Альтернатива — перезапустить экран варки после сохранения — давала бы мигание и сбрасывала бы состояние.

## Risks / Trade-offs

- [`AnimatedContent` внутри `LazyColumn` рядом с `animateItem` может дёргаться при одновременной вставке и раскрытии] → проверено на эмуляторе записью экрана: сворачивание и сдвиг соседей плавные.
- [Фокус и клавиатура: поле внизу списка уходит под закреплённые кнопки] → клавиатура сжимает только список: `padding` над кнопками, `consumeWindowInsets` этого отступа и `imePadding()` у `LazyColumn` (итог — большее из высоты кнопок и клавиатуры). Кнопки остаются под клавиатурой. `imePadding()` у всего `Scaffold` на телефоне давал белую полосу подложки окна и рывки при скрытии клавиатуры: экран вырастал обратно только в конце её анимации. Проверено на эмуляторе, окончательно — на телефоне.
- [Копия встроенного замораживает язык] → так решено осознанно, это указано в спеке.
- [Пустое имя документа/гонка записи при быстром повторном сохранении] → запись последовательна на главном потоке и `Mutex` вокруг IO.
- [`SegmentedListItem` может не поддерживать долгое нажатие] → `combinedClickable` поверх, с сохранением ripple и семантики.

## Migration Plan

Миграции нет: своих рецептов раньше не было. Откат — удалить чейндж. Файлы в `filesDir/recipes` старой версией просто не читаются.
