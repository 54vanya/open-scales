# Design

## Context

- Экраны сделаны отдельными Activity, чтобы системный предиктивный «назад» работал без своей анимации. Общее состояние живёт в синглтоне `ScaleRepository`, у каждой Activity своя `ScaleViewModel`.
- Таймер один на всё приложение: `ScaleRepository` ведёт его по монотонным часам (`TimerClock`), команды таймера по-прежнему уходят весам, чтобы те не ушли в авто-отключение. API: `toggleTimer()`, `resetTimer()`. Сброс уже учитывает, что `0x02 [03]` на нулевом таймере тарирует весы (см. `docs/protocol.md`).
- Флага «вес стабилен» в протоколе нет. Кадр `0x01` — это вес, поток, время и перегруз, ~10 Гц.
- Состояние приложения однопоточно (`Dispatchers.Main.immediate`), этим пользуются во всём коде.
- Настройки приложения хранятся в `AppSettingsStore` (DataStore Preferences). JSON-сериализации в проекте нет.
- Кнопки управления на главном экране срабатывают через `rememberPressAction` (касание/отпускание) и звучат через `ButtonSound.onControlPressed()`.

## Goals / Non-Goals

**Goals:**
- Вся логика рецепта (цели, распределение, текущий шаг, детектор пролива) — чистый Kotlin без Android, закрытый юнит-тестами по таблицам из спеки.
- Экран варки — отдельная Activity: навбар не мешает, back системный.
- Не заводить второй таймер.

**Non-Goals:**
- Редактор рецептов и хранение пользовательских рецептов. Будет отдельным чейнджем; тогда и появится JSON в DataStore.
- Восстановление варки после смерти процесса. Поворот и сворачивание переживаем, убитый процесс — нет.
- История варок, оценки, экспорт.
- Вибро-сигналы.

## Decisions

### 1. Пакет `recipe/`: модель и чистые функции

```
recipe/
  Recipe(id, title: Text, defaultDoseG, description: Text?, items: List<RecipeItem>)
  RecipeItem = Step(title: Text, durationS, note: Text?, targetRatio: Double?) | Hint(text: Text)
  Text = Res(@StringRes) | Plain(String)       // встроенный — из ресурсов, пользовательский (потом) — строкой
  BuiltInRecipes.hoffmannV60
  RecipeTimeline(recipe)       // старт/конец каждого шага, total; stepAt(seconds) -> index | null; itemFaded(i, seconds)
  PourDistribution.fill(targetsG, weightG): List<Double>   // f[i] = clamp(w, c[i-1], c[i]), последний без верха
  PourDetector(baselineG, thresholdG = 1.0).isPour(weightG)
```

`Text` — чтобы встроенный рецепт локализовался ресурсами (требование `app-localization`), а пользовательский рецепт в будущем хранил свою строку. Коэффициент хранится `Double`, для второй воды Хоффмана это `50.0/3`: так ровно получается 250 г при 15 г.

Режимы показа — функции поверх `fill`: «Осталось» = `c - f`, «Налито» = `f / c`. Округление (целые граммы / 2 знака унций, без «−0») — в одной функции форматирования, покрытой тестами.

**Альтернатива:** хранить прирост вместо накопительного рубежа. Отвергнута: формула с `clamp` по рубежам проще, режим «Налито из цели» показывает именно рубежи, а спека требует неубывания целей, что проверяется напрямую.

### 2. Всё внутри считается в граммах

Весы присылают вес в своих единицах. `BrewViewModel` переводит в граммы (oz × 28.349523) на входе, а при показе переводит обратно в текущие единицы весов. Доза, цели, опорный вес детектора и порог хранятся в граммах. Поэтому смена единиц посреди варки ничего не ломает.

### 3. Состояние варки — в `BrewViewModel`, время — общий таймер

```
            Далее(доза)             Старт              вес >= опора+1 г
[BEANS] ------------------> [READY] -------> [ARMED] ------------------> [RUNNING] <-> [PAUSED]
   ^         back              |  ^  повтор нажатия |                        |  время >= total
   '---------------------------'  '---------------'                         v
                                                                        [FINISHED]
```

`BrewViewModel` (своя у `BrewActivity`, переживает поворот) хранит фазу, дозу и опорный вес. Время берётся из `repository.state.timeSeconds`:
- ARMED → RUNNING: `resetTimer()`, затем `toggleTimer()`. Сброс нужен, потому что общий таймер мог идти на вкладке «Весы».
- Пауза / Продолжить: `toggleTimer()`.
- `timeSeconds >= total` в RUNNING: `toggleTimer()` (пауза) и фаза FINISHED. Проверка — в `collect` состояния репозитория; секундный тик уже приходит в `state`.
- Завершить: если таймер идёт — пауза, потом `finish()`.

Фаза `PAUSED` производная от `timerState` репозитория, а не отдельный флаг. Так она сама отражает паузу, если на весах включена синхронизация таймера и кнопку нажали на корпусе.

**Альтернатива:** отдельный таймер варки внутри ViewModel. Отвергнута: у весов остановится свой таймер и сработает авто-отключение посреди пролива, а на вкладке «Весы» будет показано другое время.

### 4. Детектор пролива — прямо по кадрам

В ARMED `BrewViewModel` слушает `state.weight`. Первое значение `>= baseline + 1 г` переводит варку в RUNNING. Без окна и сглаживания (решение пользователя: показания не буферизуем). Шум DOT в покое — десятые доли грамма, поэтому 1 г с запасом.

### 5. Навигация на главном экране

`MainActivity` получает обёртку: `ShortNavigationBar` (M3 Expressive, индикатор-пилюля) в портретной ориентации и `WideNavigationRail` (свёрнутая) в альбомной. Критерий тот же, что уже выбирает две колонки: ширина больше высоты. Вкладка — `rememberSaveable` (enum `MainTab`). Нынешний `DashboardScreen` становится содержимым вкладки «Весы» без изменений внутри. Верхняя панель (имя весов, заряд, поиск, настройки) общая для обеих вкладок.

Для нижней панели Scaffold `DashboardScreen` должен получать отступ снизу. Проверить, что минимальная высота карточки и прокрутка считаются от уменьшенной высоты.

**Альтернатива:** Navigation Compose. Отвергнута по той же причине, что раньше: свой переход и back. Вкладки не создают записей в стеке «назад», им навигация не нужна.

### 6. `BrewActivity` с двумя шагами внутри

`BrewActivity` (id рецепта в extras) рисует `BeansScreen` или `StepsScreen` по фазе. Back обрабатывается `BackHandler`:
- BEANS — нет обработчика, системный back закрывает Activity;
- READY — `BackHandler` возвращает в BEANS (шаг внутри экрана, без анимации, осознанно: это смена содержимого, а не навигация);
- ARMED…FINISHED — `BackHandler` показывает `AlertDialog` «Завершить варку?».

«Завершить» закрывает Activity через `finish()`, под ней остаётся `MainActivity` на вкладке «Рецепты». Удержание экрана — тот же `view.keepScreenOn` по `appSettings.keepScreenOn`, как в `MainActivity`.

### 7. Прокрутка — плавная, к верхнему краю

`LazyColumn` + `LaunchedEffect(currentStepIndex)` → `listState.animateScrollToItem(index)`. Главное теперь на табло, поэтому текущий шаг ставится к верхнему краю, а не на треть: пройденные шаги не занимают место. `LazyListState` сам упирается в конец списка. Цвет выделения и прозрачность пройденных шагов меняются через `animateColorAsState`/`animateFloatAsState` (решение пользователя: переходы по шагам плавные). Числа не анимируются — показания должны появляться сразу.

### 7а. Табло пролива

Чистая функция `PourFocus.of(recipe, timeline, doseG, weightG, seconds)` в `recipe/` выбирает шаг воды: `min(первый шаг с целью, где w < c − 1 г; последний шаг с целью, начавшийся по времени)`. Второе ограничение не даёт табло прыгнуть на следующую цель в момент её набора. Возвращает индекс шага воды, его цель, разницу `c − w` без ограничения и состояние `BELOW/AT/OVER` (порог 1 г). Крупное значение: в режиме «Осталось налить» — `c − w`, в режиме «Налито из цели» — `w` против `c`; с точностью весов (граммы — десятые, унции — сотые), тем же форматированием без «−0», что и значения шагов, но с числом знаков единиц весов. Распределение в карточках остаётся прежним (clamp по рубежам).

Табло — композабл над `LazyColumn`. Цифры — `WeightTextStyle`/`DigitsTextStyle` с `TextAutoSize`: крупно, но без обрезки на узких экранах и в альбомной ориентации, где табло занимает левую колонку.

### 7б. Сигналы шагов

`BrewViewModel` сам решает, когда сигнал: смена `timeline.stepAt(seconds)` после начала пролива (включая переход в «нет шага» в конце) и первый вход в `AT` для каждого шага с целью. Вызывает инъецированный `signal(kind)`. Звучать или нет, решает `ButtonSound.onStepSignal(kind)` по настройке `stepSignals`. Двойной сигнал — два `beep` с паузой 150 мс в скоупе `ButtonSound`. Прогрев звукового тракта включается, если включён звук кнопок или сигналы шагов. Так логика событий тестируется в `BrewViewModelTest` без звука.

### 8. Кнопки варки — общий `rememberPressAction`

`rememberPressAction` и кнопки с `ButtonSound` выносятся из `DashboardScreen` в `ui/components`, чтобы «Тара», «Старт» и «Пауза» на экране варки срабатывали и звучали одинаково с главным экраном. «Стоп» открывает диалог, без сигнала.

### 9. Настройка режима

`AppSettings.stepWeightMode: StepWeightMode { REMAINING, POURED }`, ключ DataStore `step_weight_mode` (строка enum), по умолчанию REMAINING. Строка в разделе «Приложение» `SettingsScreen` — выбор из двух вариантов тем же компонентом, что у «Темы».

### 10. Вкладка «Рецепты» без весов

Сообщение и кнопка подключения повторяют баннер вкладки «Весы» (тот же компонент и тот же `onConnect`). Рецепты рисуются неактивными (`enabled = false`), а не прячутся: пользователь видит, что его ждёт.

## Risks / Trade-offs

- [Порог 1 г сработает от толчка воронки или капли при установке чайника] → Опора берётся в момент «Старт», а не при входе на экран. Если на телефоне будет ложный старт, порог — одна константа.
- [Таймер общий: «Завершить» оставляет время на вкладке «Весы»] → Так и задумано по спеке. Сброс — обычной кнопкой «Сброс».
- [Синхронизация с таймером весов включена, и весы не подтвердили старт] → Время в варке не пойдёт, пока не пойдёт таймер репозитория. Это то же поведение, что на главном экране (оптимистичный старт с откатом). Ошибка уходит в snackbar экрана варки.
- [Смерть процесса посреди варки] → Варка теряется, Activity восстановится на шаге «Зерно». Для первой версии приемлемо, отмечено в Non-Goals.
- [Отступ под нижнюю панель ломает минимальную высоту карточки на маленьких экранах] → Сценарии «Экран ниже минимума» и «Узкий экран» проверяются на `emu-narrow`.

## Migration Plan

Миграции данных нет: одна новая настройка со значением по умолчанию. Откат — удаление вкладки и Activity, ключ DataStore останется неиспользованным.
