# Design

## Context

Мотивация — в `proposal.md`. Что важно для подхода:

- Цели шагов накопительные (`Recipe.targetsByPart`), и всё, что показывает воду, выводится из одного числа на шаг: `PourFocus` (состояние `BELOW/AT/OVER` по ±1 г, `leftG`, доля полосы, идеальный уровень), `PourDistribution.fill` (границы между шагами), «вода улеглась» в `BrewViewModel` (`leftG < SETTLE_LEFT_G`).
- Табло рисует `PourBoard` в `BrewScreens.kt`: крупное число — `BigReading` с автоподбором шрифта (32 sp … размер показаний), рядом серая единица; полоса — `PourBar(fraction, pace, over)`. Высота табло не должна меняться.
- Свои рецепты — JSON с `ignoreUnknownKeys = true`; версию формата поднимали только для тары, потому что старое приложение прочло бы её неверно.
- Спецификация полосы запрещает анимацию, а пользователь в целом за системное поведение без своих анимаций. Плавное появление второй цифры он попросил явно — это осознанное исключение.

## Goals / Non-Goals

**Goals:**
- Диапазон как свойство шага воды, с минимальным расширением существующей модели и без влияния на шаги ниже.
- Поведение табло, одобренное по макету: расстояние до зоны крупно, вторая цифра «до max» внутри зоны.
- Свои рецепты с диапазоном не ломают приложение без диапазонов.

**Non-Goals:**
- Диапазон у последнего рубежа части и диапазон итога воды.
- Выбор коэффициента перед варкой.
- Диапазоны в других встроенных рецептах, кроме цветения «V60 по Хоффману».
- Изменение сигналов шагов, детектора пролива, тары.

## Decisions

**1. Поле `targetMaxG: Int?` у `RecipeItem.Step`, а не новый вид шага.**
Шаг с диапазоном во всём, кроме зоны попадания, — обычный пролив: время, часть рецепта, накопительный рубеж. Новый вид в `sealed interface` потребовал бы ветки во всех `when` (формат, черновик, список, редактор) ради одного числа. Проверки в `init`: максимум только при заданной цели, больше неё; в `Recipe.init` — максимум не больше следующего рубежа в части, у последнего рубежа части его нет. Неверный рецепт из документа, как и сейчас, даёт `null` в `RecipeFormat.decode`.

**2. Рубеж шага с диапазоном для всех соседей — min.**
`targetsByPart`, `defaultTargetsG`, `finalTargetG`, `totalWaterG` продолжают отдавать min. Отсюда бесплатно: список шагов и полоса следующего шага статичны, прибавки и сводка редактора не меняются. Альтернатива — считать границей фактически налитое в зону — сделала бы цели шагов ниже зависящими от хода варки. Максимум, пересчитанный на дозу, нужен только там, где показывается сам шаг: его несёт `PourFocus` (новое поле, по умолчанию равное цели) и `StepWater`.

**3. Вся логика зоны — в `PourFocus`.**
`leftG` становится расстоянием до зоны (`min − w`, 0, `max − w`), `state` сравнивает с min − 1 и max + 1, `fraction` делит на `max − p`, `paceFraction` умножается на `(min − p) / (max − p)`. Добавляются доля начала зоны на полосе и «сколько можно до max» (`null` вне зоны). У шага без диапазона max = min, и все формулы совпадают с нынешними — существующие тесты `PourFocusTest` остаются регрессией. «Вода улеглась» не меняется: условие `leftG < 3` уже верно для расстояния до зоны (внутри зоны оно 0, при переливе отрицательно).

**4. Режим «Сколько налито» у самого шага ограничен max, а не min.**
Иначе при 40 г в списке стояло бы «30, налито из 30–45 г», что читается как ошибка. Значения шагов в этом режиме и так не обязаны складываться в вес.

**5. Вторая цифра — отдельный элемент в строке крупного числа, вне его автоподбора.**
`AnimatedVisibility` со стандартными `expandHorizontally + fadeIn` / `shrinkHorizontally + fadeOut` и параметрами по умолчанию: строка центрируется сама, поэтому крупное число сдвигается той же анимацией ширины. Свои кривые и длительности не вводятся. Текст второй цифры при каждом кадре просто подставляется. Шрифт — как у таймера в углу табло. Альтернатива — резервировать место всегда — отвергнута пользователем («только внутри зоны»).

**6. Оттенок зоны и второй цифры — пара ролей темы.**
Участок зоны на дорожке — контейнерный тон, вторая цифра — его основная роль (например, `tertiaryContainer` / `tertiary`), чтобы они читались как одно и отличались от заполнения (`primary`) и от цвета ошибки. Конкретная пара выбирается по скриншот-тесту в светлой и тёмной теме и одобряется по эталону.

**7. `PourBar` получает долю начала зоны.**
Зона рисуется на дорожке до заполнения, без зазоров, без анимации. `null` — шаг без диапазона, полоса как сейчас.

**8. Формат: необязательное `targetMaxG` в `ItemDto.Step`, версия не поднимается.**
Старое приложение игнорирует поле и варит по min — деградация мягкая и верная по смыслу. При пересохранении старым приложением максимум теряется; это приемлемо. `explicitNulls = false` уже гарантирует, что у шагов без диапазона поля в документе нет.

**9. Редактор: `DraftItem.Step.targetMaxG: String`, поле `DraftField.TARGET_MAX`.**
Три новые проблемы: не число или не больше min; больше следующего рубежа (с числом для текста, как `previousG` у убывающего рубежа); диапазон у последнего пролива части. Ошибка ставится на поле максимума и тогда, когда пользователь опустил рубеж следующего шага ниже него. `duplicate` сдвигает обе границы на прибавку; пересечение с оригиналом ловит проверка при сохранении.

**10. Подпись цели — одна функция форматирования диапазона.**
«30–45 г», «1.06–1.59 oz»: обе границы через `formatStepWeight`, единица один раз. Используется в списке шагов, подписи табло, предпросмотре рецепта и свёрнутом шаге редактора.

## Risks / Trade-offs

- [Вес дрожит у границы 30.0 г, и вторая цифра то появляется, то уходит] → Шум весов около 0,1 г, пролив проходит границу за доли секунды; гистерезис не вводим, чтобы не буферизовать показания. Проверить на виртуальных весах с `sim noise 0.1` и на телефоне.
- [Строка крупного числа стала шире: автоподбор ужимает число, особенно в унциях и на 320 dp] → Скриншот-тесты внутри зоны на 411 dp, 320 dp и в ландшафте; вторая цифра вне автоподбора, при нехватке места уменьшается только крупное число.
- [Анимация противоречит привычному правилу «без своих анимаций»] → Только появление и уход одного элемента стандартной анимацией Compose; числа и полоса не анимируются, это записано в спецификации.
- [В Robolectric анимация появления может дать нестабильный кадр] → Скриншоты снимаются в установившемся состоянии (вес внутри зоны с первого кадра).
- [Старое приложение пересохранит рецепт и потеряет максимум] → Принято; рецепт остаётся верным с целью min.
- [Сценарии существующего требования «Табло пролива» про цветение формально описывают одну цель 30 г] → Числа в них остаются верными (min = 30 г); отличия шага с диапазоном вынесены в отдельное требование, чтобы не переписывать блок целиком.

## Migration Plan

Миграции данных нет: документы без `targetMaxG` читаются как раньше. Меняется только встроенный рецепт; свои копии Хоффмана, сделанные раньше, остаются с фиксированными 30 г. Откат — обычный revert; рецепты с максимумом после отката читаются как фиксированные.
