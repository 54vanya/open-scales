# Design

## Context

- Вся работа с весами идёт через интерфейс `BleTransport`. Транспорт создаёт `transportFactory(address)` в `OpenScalesApp`, в debug его оборачивает `LoggingBleTransport`. Сессия, handshake, очередь команд, таймер и переподключение живут выше и про транспорт ничего не знают.
- Debug-возможности уже устроены двумя способами. Первый: объект в `main`, который создаётся только при `BuildConfig.DEBUG` (`bleJournal`). Второй: Activity в `app/src/debug`, которую `main` открывает по имени класса (`JournalActivity`).
- В тестах есть `FakeBleTransport`: отвечает на чтения из `readResponses`, подтверждает записи, умеет отказывать (`rejectedWrites`), молчать (`silentCommands`) и падать на подключении. Кадры веса сам не шлёт — тесты подают их вручную и рассчитывают на это.
- Состояние приложения однопоточно (главный поток), это допущение используется повсюду.
- Экран поиска рисует список только при `BlePrerequisite.OK`. Главный экран пробует авто-подключение тоже только при `OK`, а баннер при выключенном Bluetooth показывает причину вместо фазы.

## Goals / Non-Goals

**Goals:**
- Виртуальные весы проходят через тот же код сессии, что и настоящие: проверяем приложение, а не заглушку экрана.
- Один эмулятор протокола для тестов и debug-сборки.
- Команды из терминала детерминированы: без шума вес в кадрах ровно тот, что задан.

**Non-Goals:**
- Панель управления на телефоне.
- Эмуляция TES08 (старый протокол) и моделей, кроме DOT.
- Эмуляция сопряжения, ошибок GATT и таймаутов подключения: это уже покрывают тесты на `FakeBleTransport`.
- Сценарии из файла (скрипты пролива). При нужде — несколько команд подряд из `dev.sh`.

## Decisions

### 1. Ядро эмулятора — в `main`, пакет `sim/`, чистый Kotlin

```
sim/
  ScaleEmulator(nowMs)     // состояние весов: вес, тара, единицы, таймер, заряд, имя, отказы;
                           // onWrite(frame) -> ответные кадры; weightFrame() -> кадр 0x01
  SimulatedBleTransport    // BleTransport поверх общего на приложение ScaleEmulator:
                           // connect() падает при drop, пока подключён — тикер 10 Гц шлёт weightFrame()
  ScaleSimulator           // синглтон debug: эмулятор, адрес/имя виртуальных весов, текущий транспорт,
                           // execute(command): String — разбор команд и ответ для status
```

Экземпляр `ScaleSimulator` создаётся в `OpenScalesApp` только при `BuildConfig.DEBUG`, как `bleJournal`. В release поле равно `null`, код недостижим, и R8 его вырезает.

`FakeBleTransport` становится тонкой обёрткой над `ScaleEmulator`. Ответы на чтения, подтверждения записей и отказы делает ядро. Хуки транспорта (`services`, `bond`, `connectError`, `cccdError`, `onCreateBond`, `silentCommands`, `frames`) остаются в самом `FakeBleTransport`. Прежнее API (`readResponses`, `rejectedWrites`, `emitFrame`, `emitWeight`, `disconnectFromDevice`) сохраняется, чтобы тесты не переписывать. Тикера у `FakeBleTransport` нет, поэтому детерминизм тестов не меняется.

**Альтернатива:** ядро в `app/src/debug`. Отвергнута: общий `src/test` компилируется и для release-варианта, и `testReleaseUnitTest` не соберётся, если тесты зависят от debug-кода.

### 2. Вес считается от времени, а не хранится кадрами

`ScaleEmulator` хранит опорный вес и активный пролив: начало, длительность, прирост. Вес в момент `now` — это опорный вес плюс линейная доля пролива, минус тара, плюс шум. Поток — разность веса сейчас и секунду назад, её тоже можно посчитать из этой формулы. Так `pour` не зависит от частоты тикера, а тесты ядра проверяют вес в любой момент виртуального времени.

Кадр `0x01` кодирует вес в текущих единицах: граммы ×10 или унции ×100, как делители `WeightUnit`. `unit` меняет единицы и шлёт кадр `0x06`, как при нажатии на корпусе. Декодер приложения берёт единицы из последнего `0x06`.

Таймер весов — это `TimerClock`-подобная пара «момент запуска + накопленное», секунды идут в байтах 6–7 кадра веса. Сброс при нулевом таймере работает как тара: это известная особенность DOT (`docs/protocol.md`), и сессия её обходит. Эмуляция нужна, чтобы обход проверялся на экране.

### 3. Управление: явный broadcast в debug-приёмник

`app/src/debug`: `SimControlReceiver`, в debug-манифесте `exported="true"`, action `dev.openscales.SIM`. Команда приходит одной строкой в extra `cmd`, её разбирает `ScaleSimulator.execute`. Ответ (ошибка или `status`) возвращается через `setResultData`: `am broadcast` печатает его в терминал. `tools/dev.sh sim …` шлёт явный broadcast (`-n dev.openscales/.debug.SimControlReceiver`), чтобы не упереться в ограничения неявных broadcast'ов, и печатает только `data`.

Приёмник работает на главном потоке — там же, где всё состояние сессии, так что синхронизация не нужна.

**Альтернативы:**
- Свой сокет или HTTP в приложении — лишний сетевой код и разрешение `INTERNET`.
- Файл-очередь через `adb push` — нет ответа для `status`, нужен опрос.

### 4. Виртуальные весы в поиске и обход проверки Bluetooth

- Адрес виртуальных весов — `02:00:5C:A1:E0:01`. Это локально администрируемый MAC: с настоящими весами не пересечётся, а `SavedDeviceStore` хранит его как обычный. `transportFactory` для этого адреса отдаёт `SimulatedBleTransport`, обёрнутый в `LoggingBleTransport`.
- `ScanScreen` получает необязательный `virtualScale: DiscoveredScale?`. `ScanActivity` передаёт его из `app.simulator`, в release там `null`. Строка рисуется отдельной секцией над списком и над карточками «нет разрешения / Bluetooth выключен». Касание подключает так же, как касание найденных весов. Подпись секции — строковый ресурс в `main`: `ScanScreen` в `main` не может ссылаться на ресурс только из debug.
- Проверка «можно ли подключаться» в `MainActivity` (авто-подключение, `onConnect`) и в баннере считается пройденной, если текущие или запомненные весы виртуальные. Для этого — одна функция `app.isVirtual(address)`, в release всегда `false`.

**Альтернатива:** подмешивать виртуальные весы в результаты `ScaleScanner`. Отвергнута: сканер работает только при включённом Bluetooth и с разрешениями, а на эмуляторе Android это как раз то, чего нет.

### 5. Тикер и жизненный цикл

`SimulatedBleTransport` запускает тикер в `appScope` после `enableNotifications` и останавливает его в `close()` и при `drop`. Один эмулятор живёт всё время процесса: вес, тара и таймер переживают переподключение, как у настоящих весов. `drop` шлёт текущему транспорту `Disconnected`, после чего `connect()` новых транспортов бросает `BleException`, пока не придёт `back`. Задержка подключения — 300 мс, как у `FakeBleTransport`, чтобы фазы были видны.

### 6. `tools/dev.sh`

Подкоманда `sim` вызывает `am broadcast` и вытаскивает `data="…"` из вывода. Заодно все вызовы `gradlew` в `dev.sh` получают `--no-watch-fs`: на этой машине вотчер файлов Gradle зависает в `NativeFileWatcher.startWatching0`, и `dev.sh install/test/check` висели бесконечно. В `CLAUDE.md` появляются описание `sim` и заметка про флаг.

## Risks / Trade-offs

- [Эмулятор расходится с реальными весами] → Ответы и форматы берутся из `docs/protocol.md` и из кадров журнала DOT. Виртуальные весы нужны для проверки экранов, а не протокола, поэтому проверки на железе в чейнджах остаются.
- [Экспортированный приёмник в debug принимает команды от любого приложения на устройстве] → Он есть только в debug-сборке и меняет только состояние виртуальных весов.
- [Смена `FakeBleTransport` ломает тесты сессии] → Прежнее API сохраняется. Критерий готовности — все существующие тесты зелёные без правок сценариев.
- [Код эмулятора попадёт в release] → Проверка задачей: в release-APK нет классов `dev.openscales.sim` (`apkanalyzer dex packages`).

## Migration Plan

Миграции нет. Откат — удаление пакета `sim/`, приёмника и строки в поиске. Если виртуальные весы были запомнены, при откате приложение будет безуспешно пытаться подключиться к несуществующему адресу, пока их не забудут. Это касается только debug-сборки разработчика.
